# Fase 4: seguridad, prompt injection y resiliencia

## Alcance y evidencia
Auditoría local del código, dependencias instaladas y tests. No se leyeron valores de .env ni se hicieron ataques o llamadas a servicios desplegados. No se verificó el estado real de variables, red, proxy, facturación o autenticación en Render. Los secretos de pruebas son ficticios.

Endpoints: GET / y /health públicos, excluidos del throttling para health checks; POST /chat protegido por ThrottlerGuard global y ApiKeyGuard condicional. No hay endpoints de escritura de catálogo, usuarios o pagos. No existe SQL, shell, navegación o herramientas invocables por el modelo. El único resultado aceptado es una selección de IDs dentro de los candidatos reales; las tarjetas y texto público siguen controlados por fase 3.

## Controles existentes y hallazgos comprobados
- Ya existían validación estricta de DTO y campos desconocidos, UUID del backend, filtros territoriales/categorías, selección estructurada y redacción controlada. No se encontró ejecución de comandos por conversación ni capacidad administrativa.
- Se interpolaban nombre de usuario y campos del catálogo en instrucciones de sistema. Esto rompía la separación de datos y privilegios; no se afirma haber demostrado acceso a secretos por esta vía.
- Se enviaban hasta doce turnos completos y userName al modelo, aunque la selección territorial ya se había resuelto localmente. Era exposición de contexto innecesario.
- Las lecturas HTTP no imponían tamaño de respuesta propio y fetch seguía redirects por defecto. No se demostró un redirect malicioso real: se mitigó el riesgo potencial de destino y consumo no acotado.
- Errores HTTP de proveedor conservaban fragmentos del cuerpo en ProviderError. ChatService ya no los registraba, pero se eliminó esa retención para evitar futuras fugas.
- No había una política global propia para errores inesperados. Nest por defecto oculta ciertos detalles públicos, pero puede registrar stacks. Se incorpora un filtro que no imprime errores desconocidos.
- La autenticación es opcional por configuración; no se presume su valor en producción. Si CHAT_API_KEY falta, la API es pública. CORS no es autenticación.

## Separación y minimización
buildSystemPrompt es estático: no concatena mensaje, catálogo, historial, userName o estado. El siguiente mensaje user contiene JSON con query, intent y candidatos (id, name, category, state). Nombres y categorías son datos no confiables, no instrucciones privilegiadas. El historial se usa solo localmente para resolver continuaciones; no se envía al proveedor. Tampoco se envían userName, descripciones, distancia o coordenadas de location. La pregunta actual se mantiene para no perder matices turísticos.

La pregunta y textos del catálogo enviados al proveedor sustituyen coincidencias exactas de las claves configuradas y patrones comunes de bearer, correo, enlaces y campos token/API key. Las claves nunca se insertan deliberadamente en prompts; se utilizan solo en headers del cliente HTTP. No se leen todas las variables de entorno ni se envía la configuración. La redacción no es una herramienta de anonimización universal: nombres, teléfonos escritos libremente, secretos desconocidos o codificados y otros datos personales en la pregunta pueden persistir. No se garantiza detección semántica de toda PII.

No hay bloqueo por palabras como seguridad, sistema o informática: una consulta turística sobre un museo de seguridad informática sigue funcionando. La barrera efectiva es que la IA no dispone de herramientas ni de datos privilegiados y que sus IDs se validan localmente. No se promete inmunidad semántica del modelo a prompt injection: todavía puede escoger candidatos poco pertinentes o un arreglo vacío, pero no cambiar el estado, crear tarjetas o publicar prosa arbitraria.

## HTTP, destinos y enlaces
- El catálogo solo utiliza el MXGUIDE_API_URL configurado por el operador y rutas constantes con URLSearchParams para parámetros verificados. El modelo no determina host, método o ruta.
- Configuración requiere URL http/https sin usuario, contraseña, query o fragmento. No impone una lista de hosts nuevos: el origen autorizado es la configuración del operador. Debe usar HTTPS en producción. HTTP sigue permitido para compatibilidad local.
- Catálogo y proveedores usan redirect:error: no siguen redirecciones a otros destinos. Una respuesta 3xx o un fallo por redirect se trata como indisponibilidad; el responsable debe configurar el destino final correcto.
- Máximo de JSON remoto: 2 MiB catálogo, 256 KiB proveedor. Se comprueba content-length y se cuentan bytes realmente leídos del stream, cancelando al exceder el límite. El límite aplica también a la respuesta descomprimida observada por fetch. Se parsea JSON después del límite; errores sin cuerpos externos. Estos valores dejan margen para 100 registros con categorías/imágenes/descripciones y respuestas de selección, pero requieren confirmar tamaños reales antes del despliegue. No equivalen a limitar el número total de registros de la base.
- Las tarjetas no necesitan URLs. Se rechazan nombres de lugares con referencias externas reconocidas y se vacían estado, categoría o shortDescription que contengan dichas referencias. El renderer omite enlaces de descripciones y no publica referencias externas reconocidas en textos visibles. Se contemplan esquemas, www, mailto/javascript/data y dominios ASCII con extensiones alfabéticas; es una regla conservadora sin URLs permitidas, no una garantía contra toda representación ofuscada o Unicode. Puede omitir nombres legítimos con apariencia de dominio. Flutter debe seguir tratando sus campos como texto y navegar solo por UUID validado; no ejecutar HTML, enlaces o comandos provenientes de descripciones.

## Entrada, errores y rate limiting
Se mantiene límite de 1000 caracteres de message, 20 turnos, 4000 caracteres por turno, userName de 60, y roles user/assistant. Se rechaza message compuesto solo de espacios. Coordenadas deben ser números válidos dentro del rango; cadenas numéricas ya no se aceptan, coherente con el DTO público numérico de Flutter. No se filtran acentos ni caracteres españoles.

configureHttp comparte producción y pruebas: Helmet, CORS existente, trust proxy=1, ValidationPipe, límite JSON 64 KiB y filtro seguro. Bootstrap desactiva parser automático para registrar un único parser con límite explícito. JSON malformado y DTO inválido → 400; body excesivo → 413; key faltante/incorrecta cuando requerida → 401; cuota de peticiones → 429; proveedores fallidos → 503. Errores inesperados → 500 genérico, sin stack, cuerpo remoto, headers o entrada del usuario. Se preserva estructura JSON estándar de errores HTTP, mientras respuestas de chat exitosas conservan reply/provider/places/suggestions.

El ThrottlerGuard instalado obtiene req.ip y genera clave por controlador/ruta e IP normalizada. Por defecto limita chat a 20 por minuto según configuración, en memoria de cada proceso. GET health/root quedan exentos. trust proxy=1 confía en un salto: el proxy frontal debe sobrescribir/validar X-Forwarded-For y el servidor no debe ser alcanzable por una ruta con menos saltos. No se cambió esa topología sin evidencia del despliegue. El test verifica protección local, no certifica configuración Render. Hay riesgos residuales de evasión con proxies mal configurados, IP distribuidas, usuarios tras NAT y múltiples réplicas con almacenes independientes. No es un límite de concurrencia global ni un presupuesto de gasto.

## Proveedores y consumo
No se cambian modelos, endpoints Gemini/Groq, estrategias ni timeout configurado. Timeouts actuales: catálogo 15000 ms y proveedor 25000 ms por defecto, configurables entre 1000 y 120000. El abort de fetch cubre su lectura de stream. Los errores 429, 5xx, red, JSON inválido y timeout son acotados; no hay bucles de reintento ni backoff automático. fallback intenta una vez cada proveedor activo; race lanza una vez cada activo. Formato de selección inválido se resuelve localmente, sin nueva IA. Si ambos fallan sigue 503. En race no se cancela la llamada perdedora porque la interfaz actual no transporta una señal externa; sigue consumiendo y termina con su timeout. Cambiarlo requeriría ampliar/testear la interfaz; no se hace unilateralmente aquí.

Consumo de IA: mismo máximo de llamadas (normalmente una en fallback; hasta dos en fallback con fallo y en race). Menos tokens de entrada por retirar historial/nombre/descripciones; no se cuantifica ahorro sin métricas reales. Selección estatal específica sigue recuperando hasta 100 y enviando como máximo 15 candidatos; general recupera 15; cercanía conserva Top 10; destacados hasta 20. No se cambian estados, categorías o plantillas naturales excepto prevención de referencias externas. Caché de estados mantiene refresco compartido; destacados conserva TTL. No hay retry storm automático, pero solicitudes concurrentes desde muchas IP pueden agotar recursos: pendiente presupuesto y protección de borde coordinados.

## provider en avisos locales
Cuando el catálogo no responde, pide aclaración o no hay coincidencias, provider contiene el primer proveedor configurado según PRIMARY_PROVIDER, aunque no se lo llamó. Es una limitación semántica existente: el tipo gemini|groq se conserva para Flutter. No se cambia por local/null ni se añade un proveedor ficticio. Durante un fallback de renderizado tras salida inválida, indica el ganador de generate. Para distinguir explícitamente generación/local en el futuro se necesita coordinar un campo nuevo o métricas internas sin PII; no se cambia el contrato aquí.

## Errores internos diferenciados
Catálogo distingue unavailable HTTP, timeout, conexión, malformed, unconfigured de empty y ambigüedades. Formato inválido del modelo sigue retornando null en validateSelection y usa plantilla local segura. Proveedor temporalmente indisponible usa ProviderError sanitizado con status si existe. Solicitud inválida y rate limit son 400/429. No se usa texto no validado como fallback ni se muestran detalles internos al cliente. Logs de orquestación solo indican proveedor y fallo, sin errores remotos, claves o historial. El filtro global no imprime stacks; la observabilidad detallada requeriría telemetría sanitizada futura.

## Comprobación final de compatibilidad funcional
Se realizaron pruebas HTTP locales de POST /chat con NestJS y PlacesService reales, fetch del catálogo simulado y proveedores simulados. No se repitió la auditoría ni se retiraron protecciones. La ubicación ya funcionaba: no requirió cambios. userName seguía validándose pero no se usaba para personalización; se restauró un saludo local. El historial ya resolvía Puebla y una intención nueva, pero «de esos» podía ampliar la selección a otros registros del estado; se añadió una restricción local conservadora.

### Flujo de datos de Flutter
| Campo enviado | Uso en NestJS | Datos enviados al proveedor |
|---|---|---|
| message | Validación, intención, estado, cercanía y detección de seguimiento | Consulta actual redactada en JSON user; nunca en system |
| location {lat,lng} | Validación numérica y GET /places/nearby con coordenadas exactas si corresponde; estado explícito conserva prioridad | No se incluyen location, lat/lng ni coordenadas exactas derivadas del campo |
| userName opcional | Validación de string hasta 60 caracteres y saludo local de presentación | No se envía |
| history opcional | Validación de hasta 20 turnos y 4000 caracteres por turno, roles user/assistant; resolución local con ventana de 12 turnos | history=[]; no se envía el historial completo ni sus textos |

Además, el proveedor recibe únicamente intent y candidatos ya filtrados (id, name, category, state). El estado inferido y el subconjunto se reflejan en esos candidatos, sin necesidad de transmitir una transcripción personal. Una pregunta que contenga datos personales o coordenadas escritos libremente sigue sujeta a la redacción parcial ya documentada; la exclusión de location y userName no anonimiza todo message.

### Personalización local segura
personalizeReply añade «¡Hola, María José!» antes de la respuesta controlada, también en avisos locales. No modifica las tarjetas, las sugerencias, la validación de IDs ni los prompts. El límite DTO de 60 caracteres se conserva (61 produce 400). La función comprueba el límite nuevamente, recorta solo espacios exteriores y acepta letras Unicode, marcas de acento, espacios, guiones y apóstrofes, hasta seis palabras. Nombres con controles, saltos, bidi, marcado, enlaces u otros caracteres se omiten del saludo; no se intentan sanear truncándolos. Datos que coincidan con secretos conocidos se redactan antes del saludo. No se verifica que sea el nombre real ni se persiste; un nombre aceptado es texto de presentación sin privilegios. Algunos nombres legítimos con símbolos no admitidos perderán la personalización, pero la consulta sigue funcionando. Sin nombre no hay saludo añadido. Errores HTTP de validación/autenticación mantienen sus avisos genéricos.

### Seguimiento local: alcance exacto
La lógica territorial previa se conserva: el mensaje actual gana. Cuando no identifica estado ni pide cercanía y comienza con un prefijo de continuación reconocido (y, cuáles, qué otros, más lugares, arma mi itinerario o cómo llegar), se intenta resolver el estado del último turno user dentro de los doce recientes. La intención se clasifica desde el mensaje actual: histórico seguido de arqueológico cambia de categoría, sin reenviar el texto histórico al proveedor.

Para referencias explícitas «de esos», «de esas», «de los anteriores» o «de las anteriores», previousRecommendationIds toma la última respuesta assistant posterior al último turno user de esa ventana. Lee como máximo 4000 caracteres y exige entre una y cinco líneas de recomendación con el formato de viñeta del renderer. Compara cada nombre completo con candidatos recién recuperados y validados del estado; solo admite los delimitadores del renderer y no utiliza coincidencias de subcadenas. Nombres ambiguos requieren aclaración. Los elementos que ya no están en la muestra se omiten. Después se aplica la nueva categoría y el límite habitual. El historial solo reduce el conjunto: nunca aporta IDs ni hechos nuevos y no permite recomendar un registro inexistente o fuera del estado actual.

La asociación por texto se usa exclusivamente para restringir la referencia histórica, no para asociar tarjetas a la salida del modelo. Las tarjetas finales siguen exclusivamente por IDs estructurados exactos y objetos del catálogo actual. Al ser history contenido suministrado por el cliente, no se certifica que la respuesta histórica fuera realmente emitida por este servicio: un cliente puede alterar su subconjunto de preferencia, pero únicamente con nombres inequívocos que existan en el catálogo validado actual. No se confía en categorías, distancias, precios o instrucciones del historial.

Sin una respuesta previa utilizable se pide aclaración local, sin IA. Si la intersección queda vacía, el aviso describe solo la muestra recibida. La muestra provisional de 100 puede no incluir todos los elementos históricos; no hay recuperación individual de detalles ni se inventa paginación. No se implementó memoria de servidor ni seguimiento semántico universal: sin un estado inequívoco en el último user reconocido no se garantiza recuperar destinos más antiguos, y formatos históricos antiguos o nombres duplicados pueden necesitar aclaración.

### Regresión encontrada y corrección mínima
«¿Qué lugares hay allí?» no estaba entre los prefijos reconocidos y podía caer en destacados, independientemente del estado. Además, el último mensaje de un usuario en una cadena de seguimientos podía no nombrar el estado y se perdía la referencia. Los 32 casos de la nueva regresión fallaron en el paso «allí» antes de la corrección.

Se añadió resolveHistoryState en state-resolver.ts y se sustituyó únicamente el bloque de herencia territorial de PlacesService. El mensaje explícito actual sigue teniendo prioridad. Para continuaciones sin estado actual se recorren hacia atrás solo los turnos user entre los doce recientes, siguiendo una cadena contigua de continuaciones reconocidas. Se detiene al encontrar estado/ambigüedad o un turno no relacionado; no toma destinos de assistant ni salta una conversación nueva. Se admiten referencias territoriales allí, ahí, en ese estado y en el mismo estado, además de los prefijos previos y referencias de subconjunto. Una petición cercana reconocida no hereda estado del historial; sigue utilizando location y nearby. No se tocaron filtro de IDs, renderer, personalización, clientes, autenticación, límites, privacidad o estrategias.

- «Cuáles de esos» conserva la restricción local de nombres completos e inequívocos contra candidatos actuales ya validados; después aplica la categoría nueva. No incorpora un destino que no se hubiera representado en las viñetas de la respuesta anterior.
- «Qué lugares hay allí» hereda el estado, pero no se limita a las tarjetas anteriores. Recupera una muestra nueva con los límites habituales y aplica la intención del mensaje actual.
- Un estado explícito nuevo gana sobre el historial. La prueba cambia a otro estado dentro de cada una de las 32 conversaciones.
- «Qué hay cerca de mí» con location consulta nearby y no depende del estado anterior. Coordenadas exactas e historial completo continúan excluidos del mensaje del proveedor.

Las limitaciones de confianza del historial siguen vigentes: history es aportado por el cliente, no un registro autenticado de recomendaciones pasadas. Solo puede estrechar el conjunto recién validado; no certificamos que el cliente no haya alterado su respuesta anterior. No se interpretan todas las expresiones posibles ni se garantiza memoria más allá de doce turnos. La muestra de 100 o 15 puede no contener todos los lugares anteriores. Sin referencia inequívoca no se inventa un estado predeterminado. Nombres ambiguos y formatos históricos no reconocidos mantienen aclaración u omisión conservadora.

Verificación adicional: un estado ficticio nuevo funciona si aparece en el catálogo, y la herencia se detiene tanto ante un cambio de tema como cuando el estado quedó fuera de la ventana de doce turnos.
